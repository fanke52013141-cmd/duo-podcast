# 专家质量视频生成提速方案与实验计划

日期：2026-10-27，更新：2026-10-28。状态：已完成运行参数与注意力后端首轮实验，详细证据见PROGRESS及measurements目录；其他路线仍为待验证方案，两分钟一小时尚未验收。

## 1. 目标和决策原则

用户需求是寻找“质量达到专家版、速度可接受”的生成路线。用户已明确：两分钟视频在一小时以内可以接受；现有 MuseTalk 快速版的嘴唇抖动和融合效果不符合预期。

主验收目标：**已有已采用动作包、已确认配音时，从提交视频生成到两个机位风格中指定的一支最终视频完成检查，两分钟内容不超过60分钟。** 同框和过肩分别计时，不能把两支输出的合计耗时当成单支耗时，也不能把单支耗时冒充两支总耗时。配音合成、首次生图/动作资产准备单列；同时提供“从脚本开始制作”的累计计算时间，人工审看等待不混入性能指标。

质量基准是本轮黄瓜/茄子的专家试片，由用户认可其口型表现。基准只代表该案例，不代表任意角色或长片效果已达标。

- 先保证口型同步、嘴唇稳定、身份和融合，再比较速度。
- 对当前专家链路先做低改动成本的运行效率优化；区域生成、替代引擎和替代模型作为后续候选。
- 优化质量判定面向新生成方案，不以修补现有成片作为主要交付。
- MuseTalk 保留历史回放和对照能力，暂不作为新方案必须保留的最终交付路线；不在本批删除旧代码或改变旧工程。
- 不承诺固定提速倍数，不把未经两分钟实测的线性估算当验收。

### 2.2 实际耗时

| 路线/阶段 | 本次事实 | 限制 |
|---|---:|---|
| 真实三句配音 | 34.979秒 | 单次记录，非长稿基准 |
| 快速同框首次请求 | 30.662秒 | 包含本轮运行时初始化 |
| 快速后续同框/过肩请求 | 13.765～15.319秒 | 素材和缓存已就绪；用户认为质量不达标 |
| 专家五段引擎执行 | 158.636、147.080、147.637、122.396、75.983秒 | 一次试验，混有缓存差异，不是五次重复测量 |
| 专家引擎执行累计 | 651.732秒，约10分52秒 | 包含引擎内加载、预处理、采样、解码/输出等，不是已分离的纯GPU采样时间 |
| 专家首请求开始至最后成功 | 696.672秒 | 包含分段调度及首段检查暂停，不用于宣称连续服务性能 |

专家最终计划271帧，五段实际模型窗口为81/81/81/81/33帧，合计357帧。上下文及量化补齐相对计划多约31.7%；该帧比例不等于可以直接获得的耗时降幅。最终270帧与母轨差约2.54毫秒，是25fps帧栅格取整，母轨不变速、不平移。

按本次引擎执行总计线性推算两分钟约120.7分钟；要进入60分钟门槛，首先争取约2倍总提速。短片筛选暂以10.8秒完整生成约4.5分钟为优先候选，给长片拼接、检查和波动留余量；这是实验筛选目标，不能代替两分钟实测。

### 2.3 当前结论不能外推的地方

现有专家工作流仍是独立实验链路，未接入正式ModeVideoProvider项目路由。模型是否接受图、文件可解码、音轨相等和用户认为口型较好是四类不同证据。不能关闭原有引擎身份、任务归属、恢复或人工确认门槛来宣称上线。

原始证据在本机`.review/vegetable-expert/`、`.review/vegetable-acceptance/`；交付在仓库同级“黄瓜茄子角色验证-20261027/”。这些包含本机媒体和配置，不随代码提交。共享仓库只保存脱敏摘要、工具、测试和本方案。

## 3. 质量与稳定性验收标准

### 3.1 必须同时满足的质量门槛

| 维度 | 检查方法 | 淘汰条件 |
|---|---|---|
| 口型同步 | 同音轨、同时间轴盲标A/B；正常速度观看发音起止、闭口音和角色交接；必要时0.5倍定位 | 可感知的持续提前/滞后、错角色张嘴、明显漏动；不能靠平移音频掩盖 |
| 嘴唇稳定 | 正常速度和局部放大检查边缘、牙齿、嘴角；排除整体头动后再观察局部跳变 | 重复出现嘴角抽动、轮廓闪烁、牙齿随机闪变、贴合位置跳动 |
| 脸部融合 | 全景及脸部局部检查肤色/蔬菜表皮、亮度、边缘和体积 | 明显补丁边缘、肤色闪变、脸部漂浮、过度模糊或拖影 |
| 身份与五官 | 全片检查眼鼻嘴、角色轮廓，过肩前景额外脸检查 | 身份漂移、遮脸、五官丢失、前景生出可驱动的额外脸 |
| 结构动作与倾听 | 排除嘴部与背景的运动证据，加完整人工看片 | 把身体替换成静态、只动光线冒充动作、倾听者持续讲话、动作严重变形 |
| 接缝 | 正常速度看片，并检查各窗口/状态/机位切点前后 | 接缝跳脸、姿态突跳、闪帧、累积音画漂移 |

自动人脸检测只能报告检测覆盖率，不能替代五官自然度结论。SyncNet等同步评分若引入，必须先确认其对蔬菜人脸的适用性；不以单个分数替代用户判断。时间抖动指标也只能作辅助：真实口型和眨眼不能被误当成抖动压平。

用户对候选整体认可、各项无新增不可接受问题，才标记`qualityAccepted=true`。实验工具的默认值始终为未确认。技术失败和质量失败分别登记，不能把“有文件”当成通过。

### 3.2 媒体和运行硬门槛

- 完整严格解码；原生规格与导出规格分别记录；最终实际帧数符合统一的样本时钟和帧取整约定。
- 快速基准、专家基准和候选使用同一母轨；同编码参数下比较解码PCM。若更换封装/编码器导致压缩音频不同，另交付母轨不变的证明，不声称PCM相同。
- 无NaN/Inf、黑帧、损坏帧、OOM、驱动错误或无限等待；取消/重启后保留已完成素材，不重复提交未知结果的模型任务。
- 每次运行记录GPU整体显存与可获取的进程分配/保留峰值，不能混称；优先保留至少约1.5GiB整体显存余量。未采集到的数据写unknown。
- 同一张GPU受控串行测试；有其他重负载时不计有效性能样本。CPU准备可与GPU工作有限流水，但要防内存/磁盘争用。

## 4. 测量设计

### 4.1 冻结的输入与身份

每次运行的清单包含：动作包/媒体/坐标/母轨SHA256、源帧映射、机位、输出尺寸/FPS、原生尺寸、随机种子、完整工作流、引擎源码和节点版本、七类模型身份、Python/PyTorch/CUDA/驱动、GPU型号、启动环境、缓存状态和任务ID。

本机文件摘要只证明文件本身，不能冒充HTTP引擎已加载该文件；实验需记录实际启动程序、导入路径、节点校验与模型加载证据。正式发布继续遵守既有引擎绑定门槛。

变体只修改声明的变量，其他种子、采样步骤、音频、提示词、参考动作、输出锐化和编码保持一致。改变模型、窗口、分辨率或人物区域的实验单独分类，不能包装成同质量无损提速。

### 4.2 计时口径

| 指标 | 起止点 | 用途 |
|---|---|---|
| T_queue | 提交至实际获GPU执行权 | 服务体验，不能算模型计算 |
| T_prepare | 输入核验、PCM切片、参考编码、遮罩准备 | CPU/素材准备瓶颈 |
| T_load | 模型/节点初始化与载入 | 首次运行成本 |
| T_condition | 文本、图像、音频特征与参考VAE编码 | 重复计算和缓存机会 |
| T_sample | 实际去噪阶段 | 主要算子和传输分析 |
| T_decode | VAE解码 | 解码优化机会 |
| T_finish | 去上下文、拼接、编码、哈希与解码验证 | 最终交付成本 |
| T_total | 已获执行权、输入就绪后至最终文件检查完成的单调时钟 | 一小时主目标；并行流水时不能简单累加子项代替总时间 |

另报进程启动至交付的冷态T_total，以及含排队的用户墙钟。GPU阶段用正确的同步边界或CUDA事件测量，不能因异步提交过早停止计时。分析器本身的开销单列，不能把带重型分析器的基线与无分析器候选比较。

“模型冷态”定义为重启模型进程、权重未驻留GPU，磁盘和OS文件缓存可保留并注明；不宣称磁盘全冷。暖态保持同一引擎、模型、图和明确的缓存状态。旧基线的一次运行不能作为统计显著提速的依据。

筛选：单窗口各一次确认可运行；入围后完整10.8秒至少3次交错A/B。最终保留方案在10.8秒测试集补足相同配置冷态5次、暖态5次，报告中位数、最慢值和失败次数；每次都验证输入/模型身份和输出有效性。改变数值算子后不要求视频逐字节相同，但必须重新做质量对照。5冷/5暖不默认扩展为十次两分钟长片任务。

## 5. 实施路线A：现有专家链路运行提速（最高优先）

先做单变量筛选。每一步相对已通过的父变体运行，保留明确的父子关系和启动命令。

| 实验 | 唯一主要变化 | 固定内容 | 风险/退出条件 |
|---|---|---|---|
| A0 | 复制当前兼容环境，重现基线并分阶段计时 | 当前全部配置 | 无法重现则先处理漂移，不继续比较 |
| A1 | CUDA_LAUNCH_BLOCKING由1改为0/未设置 | CPU权重保护、38块交换和其他禁用开关 | 异步错误、错误输出或无收益即回退；不能从参数含义直接宣称瓶颈已证实 |
| A2 | 基于显存实测，交换块数38→36→32逐项试 | 选定同步设置、其余参数 | 有显存余量才继续；不一次降到0；OOM记录为失败，不自动重试原未知任务 |
| A3 | 仅允许pinned-memory，之后独立试non_blocking传输 | 固定模型/块数和CPU权重保护 | Windows/5080传输错误、主机内存异常、输出变化不可接受即回退 |
| A4 | 在兼容条件满足后单独启用async-offload，再试prefetch=1/2 | 不同时换注意力或采样 | 事件生命周期、CPU权重缓存和显存占用需实测；不能简单删除兼容shim |
| A5 | 实际支持的高效注意力后端 | 所有生成设置不变 | 先检查安装节点选项、5080内核和依赖；静默退回SDPA的运行不算成功提速 |
| A6 | 用完整LightX2V引擎对照同等InfiniteTalk能力 | 保留相同角色/音轨/质量门槛 | 先验证V2V、双人音轨、区域绑定和Windows支持；仅支持单图单人的路线不能冒充等价替换 |

注意：当前已使用加速LoRA和部分去噪，不能把“安装同一LoRA”当新增优化，也不能拿普通40步流程的宣传加速倍率套到当前2次实际去噪上。

推理期间不修改已有环境。候选引擎使用单独目录、端口和日志；共享模型只读引用。保留原始兼容启动器、依赖和完整回退命令。筛选工具默认`plan`零模型调用；实际推理必须显式选择变体。

本阶段交付：瓶颈分解、变体配置、真实媒体、配对报告和保留/淘汰清单。只有真实计时降低且质量过门槛的变体进入下一阶段。

## 6. 实施路线B：窗口、缓存与调度（第二优先）

| 实验 | 做法 | 必须验证 |
|---|---|---|
| B1 上下文 | 当前8帧对照4帧；先保持核心64帧，不改变总音轨 | 交接、闭口音、窗口边界和所有拼接点；减帧不等于同倍提速 |
| B2 长窗口 | 仅在节点/模型确有支持且显存允许后试更长核心窗口 | 当前规划器明确限制64核心/81模型帧；不能只删断言就宣称支持 |
| B3 条件缓存 | 识别重复文本/图像条件、VAE参考编码、音频条件并固定内容身份 | 缓存键包含权重/源码/精度/真实PCM/采样率/绝对位置/上下文，随机采样必须绑定seed或缓存确定性结果 |
| B4 生命周期 | 同一批相容窗口复用已加载模型，避免反复切换TTS/视频模型 | GPU互斥不变，峰值显存受控，不干扰旧引擎 |
| B5 CPU流水 | 下一窗口参考准备与当前GPU工作受限重叠 | 输入写完再提交，哈希冻结，取消清理完整，无并发覆盖 |
| B6 改稿复用 | 未变依赖的已完成窗口复用，仅重做必要受影响区间 | 改词、改时长、改机位、改编码规格的修改矩阵；上下文受影响的相邻窗口不能误复用 |

这里需要区别首次整片生成提速和修改后的增量提速。只改一句后更快，不能作为首次两分钟生成已达一小时的证据。

## 7. 实施路线C：专家人物区域生成（探索候选）

目标：减少每次重算整幅背景和无关人物的成本，同时保留专家模型的时间连续性。

实施步骤：

1. 从已采用逐帧坐标建立平滑的角色区域轨迹，覆盖完整脸、额头、下巴及必要的蔬菜表皮；不只裁嘴。区域变化只用于几何稳定，不压平真实嘴部动作。
2. 选取统一的、满足模型尺寸约束的区域输入，保留完整多帧上下文与原始角色音轨。分别比较例如256级/384级区域；最终尺寸需由模型实际支持决定。
3. 只对正在发言主体调用专家生成；倾听沿用已采用、闭口且有动作的素材。若用户需要高级倾听表演，则作为额外能力单列，不能免费计入提速。
4. 把整个生成的人脸/头部区域按同一轨迹放回原生画面，处理色彩、遮挡和融合；不以全脸模糊遮盖边缘问题。
5. 从单角色近景开始，再测同框，最后测过肩。两角色区域分别生成时，总计算量是两个调用之和；不能只按单个裁剪面积推算总提速。

主要风险：区域缩放导致五官损失、模型依赖全景上下文、融合边缘、主体摆动出框、头部与身体不一致。身体运动和前景必须保持，区域方案不是默认优于全景的结论。

退出条件：同音轨10秒对照中出现用户不接受的嘴唇抖动、补丁感或身份变化，先淘汰该尺寸/合成策略；不因快而降低质量门槛。

## 8. 实施路线D：LatentSync专用口型候选

首选小规模测试LatentSync 1.5。官方说明其加入时间层改善连续性，最低推理显存8GB；1.6最低18GB，不作为当前16GB卡的直接首选。1.5也不能预先承诺比当前专家快，或保证蔬菜人脸效果。

实施步骤：独立环境和固定权重版本→已有单角色素材确认实际检测/对齐成功→同一原始音频单角色3秒→双角色分别处理并完整计时→10.8秒A→B→A→入围后同框/过肩与长片。

重点检查其人脸对齐和时间处理是否适配非人类表皮、是否产生裁剪漂移、是否破坏倾听主体。官方建议的步数/引导参数也存在同步精度与抖动权衡，不能以提高引导强度替代验收。

依赖、权重许可、下载体积、5080/Windows兼容性先检查。仅在项目隔离环境安装，不升级共享PyTorch、ComfyUI或现有模型。

| P1 运行优化 | A1、A2；有真实瓶颈证据再进A3–A5 | P0通过 | 先筛单窗口，再跑完整10.8秒；无收益就停止该方向 |
| P2 调度优化 | B1/B3/B4优先，B2/B5/B6按瓶颈进入 | 有稳定的专家父变体 | 窗口接缝和失效矩阵通过，数据表显示真实收益 |
| P3 替代路线 | A6、C、D独立比较 | 低成本优化仍未达到短片筛选目标，或对照价值明确 | 每条先完成可运行/质量小样，不一次部署所有模型 |
| P4 质量筛选 | 原专家与最多3个入围方案盲标同音轨对照 | 技术检查通过 | 用户判定无不可接受退步，淘汰快但质量差的方案 |
| P5 长片 | 30秒后两分钟；再扩角色类型 | P4通过 | 真实两分钟单支T_total≤3600秒、完整质量检查通过 |
| P6 产品接入 | 发布开关、项目绑定、恢复UI、诊断、回退 | P5及运行稳定性通过 | 正式API/页面链路与旧工程回归；保留原专家基线可回退 |

资源安排：一张GPU串行；先用两段有代表性的短窗口（包含A及B发言）筛选，每个新变体最多一次初筛；坏图、OOM或接口不兼容即停止。入围再花时间跑完整短片和重复基准。任何单变量效果不明确，先补测，不能叠加后归因。

本机默认单次模型调用超时沿用已验证上限并记录；超过预期耗时先查原ID和队列，绝不盲目重复提交。每个运行批次设置最大任务数和总运行上限，已经完成的结果不覆盖。依赖安装或算子编译失败先归为兼容性问题，不为“必须出结果”修改共享环境。

## 10. 两分钟一小时门槛的验收方式

1. 先用真实30秒内容验证重复、拼接、切镜和音画漂移，包含A/B多轮交接、短句/长句/停顿及不同嘴型。
2. 以通过方案生成真实两分钟内容。不能用10秒片循环12次、重复静帧或仅拼接旧成片代替真实推理。
3. 初次两分钟验收限冷态一次、暖态一次；只有失败或波动需要解释时再补一次，避免一开始投入十次长片推理。发布前若需要更多长片压力测试，单列批次与资源安排。所有运行都报耗时，不能只展示最快一次。
4. 主目标是单次指定风格完整生成不超过3600秒；同时披露最慢有效运行、失败、重试与排队。如仅暖态达标，明确标为暖态达标，不能宣布首次冷态也达标。
5. 同框、过肩分别验收；修改音频后重新核对时钟。导出分辨率提高不代表模型原生画质提高。
6. 如果当前16GB硬件在质量门槛下达不到一小时，报告实际可达结果，再单列更大显存/其他部署环境的成本方案，不能隐藏降质。

## 12. 首轮可执行任务清单

1. 整理本次5个专家任务的实际执行时间、输入与输出摘要，生成baseline.json（不调用模型）。
2. 搭建白名单参数的隔离实验启动器与任务账本；默认plan不联网、不推理。
3. 对计时/身份/恢复语义做轻量专项测试；用现有真实媒体检查工具验证报告不会误写质量通过。
4. 独立启动当前兼容基线，运行两个代表窗口，记录阶段时间、显存和主机内存。
5. 仅关闭CUDA_LAUNCH_BLOCKING，对相同两个窗口作A/B；保留CPU权重保护与其他开关。
6. 有显存数据后再测试38→36块交换；确认资源余量再决定是否试32。
7. 入围者跑完整10.8秒，交付同音轨对照、总耗时表和风险说明；用户看质量后决定进入下一批。
